## 2. 필수 검증 항목별 결과

### 2.1. `PostReader(db_path)` 분리 및 안전 격리
- **존재하지 않는 DB 처리**: `PostReader("nonexistent.sqlite")` 호출 시 `FileNotFoundError`가 즉시 발생하며, 파일 시스템에 새 파일이 생성되지 않음을 확인 (`test_01_store_separation_and_missing_file_safety`).
- **Store 생성자 격리**: `raider_mcp.py` 소스 코드 정적 분석 및 네임스페이스 점검 결과, `Store` 클래스를 임포트하거나 인스턴스화(`Store(...)`)하지 않음을 확인.
- **`mode=ro` 및 `PRAGMA query_only=ON`**: `sqlite3.connect(..., uri=True)`를 통해 `mode=ro`와 `query_only`를 엄격히 적용. 연결 객체에 직접 `DELETE`, `INSERT`, `UPDATE`를 시도했을 때 `sqlite3.OperationalError: attempt to write a readonly database`로 즉시 차단됨을 실증 (`test_02_readonly_mode_query_only_and_connection_cleanup`).
- **요청 단위 연결 정리**: `PostReader._query`가 쿼리 종료마다 `try...finally: db.close()`를 수행하므로, 윈도우 환경에서도 파일 잠금이 잔존하지 않고 쿼리 직후 파일 이름 변경/이동이 정상 수행됨을 검증.

### 2.2. `list_posts` 조회 의미론 및 입력 검증
- **반환 구조**: `{'total': int, 'items': list[dict]}` 구조를 정확히 반환하며, `total`은 페이지 제한(`limit`/`offset`) 적용 전 필터 조건과 일치하는 전체 레코드 수임을 검증 (`test_03_list_posts_ordering_and_pagination`).
- **3단계 복합 정렬**: `posted_at DESC, platform ASC, post_id DESC` 정렬을 검증:
  1. `posted_at` 내림차순 최우선 (2026-03-01 > 2026-02-01 > 2026-01-01)
  2. 동일 `posted_at`일 때 `platform` 오름차순 (`bluesky` < `x`)
  3. 동일 `posted_at` 및 `platform`일 때 `post_id` 내림차순 (`post_90` > `post_10`)
- **엄격한 입력 검증**:
  - `limit`: int 1..500 경계값 정상 동작. `0`, `-1`, `501`, `True`, `False`, `"10"`, `1.5`, `None` 모두 `ValueError` 발생 거부.
  - `offset`: int >= 0 정상 동작. `-1`, `True`, `False`, `"0"`, `0.0`, `None` 모두 `ValueError` 발생 거부.
  - `platform` / `handle`: 문자열 외 `int`, `None`, `bool`, `list` 전달 시 `ValueError` 발생 거부.
- **SQL 인젝션 방어**: `' OR '1'='1`, `'; DROP TABLE posts; --`, `' UNION SELECT ...` 등의 악의적 페이로드가 파라미터 바인딩을 통해 리터럴 문자열로 정확히 처리되어 0건 일치 반환 확인 (`test_05_sql_injection_defense`).
- **페이지 경계 조건**: `offset >= total`일 때 `total`은 유지되고 `items=[]` 반환 확인.

### 2.3. `get_post` 단건 조회 및 플랫폼 격리
- **플랫폼 간 동일 ID 격리**: 플랫폼이 다르고 `post_id`가 동일한 글(`x:common_id` vs `instagram:common_id`)에 대해 각각 독립적인 글 딕셔너리를 정상 반환함을 실증 (`test_06_get_post_semantics_and_platform_isolation`).
- **미존재 ID**: 조회 대상이 없을 때 `None` 반환.
- **필수 키 검증**: `platform`이나 `post_id`가 빈 문자열 `""`, 공백 `"   "`, `None`, 정수형 등일 경우 `ValueError` 발생.

### 2.4. `list_unanalyzed` 미분석 집합 및 스키마 내결함성
- **`post_analyses` 테이블 부재 시**: 테이블을 강제로 자동 생성하지 않고, 전체 4건이 미분석으로 정상 조회됨.
- **`processing` 테이블 무시**: OCR/음성 전사용 `processing` 테이블에 완료(`completed`) 상태가 있더라도 AI 분석 완료로 간주하지 않고 미분석 목록에 그대로 보존됨 (`test_07_list_unanalyzed_comprehensive_matrix`).
- **`post_analyses` 테이블 존재 시**: `(platform, post_id)`가 일치하는 행만 정확히 배제. 중복 레코드 및 `NULL` 레코드가 테이블에 존재하더라도 쿼리 오류 없이 안정적으로 동작.
- **식별 열 누락 스키마 오류**: `post_analyses` 테이블이 존재하지만 필수 식별 열(`platform` 또는 `post_id`)이 누락된 경우, 침묵하거나 은폐하지 않고 명시적 `ReaderError("post_analyses lacks required identity columns")` 발생.

### 2.5. 원문 보존성 및 오류 위생
- **메트릭 값 구별**: `{"likes": null}`과 `{"likes": 0}`이 왜곡 없이 각각 `None`과 `0`으로 명확히 구별되어 반환됨 (`test_08_content_fidelity_unicode_none_and_corrupt_data`).
- **본문 보존**: 빈 문자열 본문(`text=""`)과 `text=None`이 원문 그대로 보존됨.
- **300k+ 유니코드 보존**: 한글·이모지·복합 문자로 구성된 300,030자의 대용량 유니코드 텍스트가 절삭이나 인코딩 손실 없이 정확히 반환됨.
- **손상 데이터 및 오류 메시지 위생**:
  - 손상된 JSON 필드(`raw="{corrupted"`) 조회 시 고정 안전 에러 `ReaderError("stored post contains invalid JSON")` 발생.
  - `posts` 테이블이 없는 DB 조회 시 고정 안전 에러 `ReaderError("database query failed")` 발생.
  - 오류 메시지 및 응답 본문에 파일 시스템 절대 경로, 임시 디렉터리 경로, 원시 SQL문, 스택 트레이스가 일절 노출되지 않음을 확인.

## 3. MCP stdio 프로토콜 및 아키텍처 경계 검증

### 3.1. 프로토콜 준수 및 도구 선언
- `FastMCP` 서버 기동 후 실제 stdio 클라이언트로 `initialize` 및 `list_tools`를 수행한 결과, 정확히 `get_post`, `list_posts`, `list_unanalyzed` 3개 도구만 노출됨 (`test_01_tool_registration_and_annotations`).
- 모든 도구에 `ToolAnnotations(readOnlyHint=True, destructiveHint=False, idempotentHint=True, openWorldHint=False)`가 정확히 설정되어 클라이언트에 메타데이터로 전달됨.

### 3.2. Direct API와 MCP SDK 간 타입 강제 변환(Coercion) 대조 분석
- **현상 관찰**:
  - Direct API (`PostReader.list_posts`): `limit=True`, `limit="2"`, `offset=False`, `offset="0"` 모두 엄격하게 `ValueError`를 발생시킴 (`_int` 함수의 `isinstance(value, bool)` 및 `isinstance(value, int)` 검사).
  - MCP stdio 클라이언트 호출 (`session.call_tool`): JSON-RPC arguments에 `{"limit": True}`를 전달하면 오류 없이 1개 아이템이 반환되고, `{"limit": "2"}`를 전달하면 2개 아이템이 반환됨 (`test_04_sdk_coercion_contrast_analysis`).
- **원인 분석**:
  - `raider_mcp.py`의 `create_server`에서 FastMCP 도구 함수의 시그니처가 `def list_posts(..., offset: int = 0, limit: int = 100)`로 정의되어 있음.
  - Python MCP SDK(FastMCP)는 내부적으로 Pydantic v2 모델을 생성하여 클라이언트의 JSON-RPC 매개변수를 검증함.
  - Pydantic v2의 기본 검증 모드는 non-strict(lax) 모드이므로:
    1. JSON boolean `true`는 정수 `1`로 강제 변환(coerce)됨.
    2. JSON string `"2"`는 정수 `2`로 강제 변환(coerce)됨.
    3. 문자열 `"bad"`는 변환 불가능하므로 Pydantic validation error (`type=int_parsing`)로 `isError: True` 반환.
  - 그 결과, Pydantic이 변환한 순수 `int` 값(1, 2)이 내부 `reader.list_posts`로 전달되어 `PostReader`의 타입 검사를 통과하게 됨.
- **평가 및 제언**:
  - Direct API 계층은 spec 요구사항대로 `bool`과 비정수 타입을 완벽하게 차단하고 있음.
  - MCP 프로토콜 계층에서는 JSON 표준 특성상 클라이언트 도구에 따라 문자열이나 불리언 형태의 수치가 전달될 수 있으며, SDK 기본 거동(lax coercion)에 의해 유연하게 정수 변환 처리되고 있으므로 기능적 결함(Crash 또는 오작동)은 발생하지 않음.
  - 향후 엄격한 JSON-RPC 스키마 검증이 요구된다면, FastMCP 도구 매개변수에 Pydantic `StrictInt`를 적용하거나 데코레이터 단에서 JSON 원본 타입을 직접 검증하는 방안을 고려할 수 있음.

### 3.3. stdio 위생 및 라이프사이클
- stdout에는 오직 유효한 JSON-RPC 2.0 메시지만 출력되며, 배너나 print 문 프로토콜 오염이 전혀 없음 (`test_05_stdio_hygiene_and_clean_shutdown`).
- stdin 닫힘 시 프로세스가 잔여 스레드나 좀비 프로세스 없이 깔끔하게 종료됨.
- CLI에서 존재하지 않는 DB를 지정했을 때 표준 에러에 `error: database not found`를 출력하고 종료 코드 2로 종료되며, DB 파일을 자동 생성하지 않음 (`test_06_missing_db_cli_exit_code_and_help`).

## 4. 무변경(Read-Only) 보장 및 WAL 모드 실증 관찰

### 4.1. 파일 불변성 검증
- MCP 도구 다중 호출(`list_posts`, `get_post`, `list_unanalyzed`) 전후로 원본 SQLite 파일의 `sha256`, `st_mtime_ns`, `sqlite_master` 테이블 목록을 비교한 결과, 바이트 단위까지 완전 일치함을 확인 (`test_02_call_tool_queries_and_null_behavior`).

### 4.2. Rollback Journal vs WAL 모드 실증 및 사이드카 관찰
- **WAL 모드 최신 커밋 가시성**:
  - `PRAGMA journal_mode = WAL` 설정 후, writer 연결에서 트랜잭션을 commit하되 checkpoint를 수행하지 않은 상태(데이터가 `.sqlite-wal`에만 잔존하는 상태)를 구성.
  - `PostReader`는 URI `mode=ro`를 사용하므로, checkpoint되지 않은 최신 커밋 데이터(`uncheckpointed_wal_2`)를 누락 없이 완벽히 조회함을 실증 (`test_09_wal_mode_uncheckpointed_visibility_and_sidecars`).
  - (참고: 만약 SQLite 연결 시 `immutable=1`을 강제하면 WAL을 열지 않아 최신 커밋이 누락되는데, 본 구현은 `mode=ro`를 사용하여 정합성을 완벽하게 유지함).
- **사이드카 파일(`-wal`, `-shm`) 관찰 사실**:
  - **관찰 1**: 활성 writer가 있는 상태에서 PostReader가 읽을 때, SQLite 엔진은 `-shm`(공유 메모리) 및 `-wal` 사이드카를 참조하며 쿼리를 수행함. 이때 DB 본체 파일의 크기 및 해시는 전혀 변경되지 않음.
  - **관찰 2**: writer가 모두 닫혀 사이드카가 없는 상태의 WAL DB를 `PostReader`(`mode=ro`)로 최초 읽을 때, SQLite 엔진의 WAL 인덱스 관리를 위해 32KB의 `*-shm` 및 0바이트의 `*-wal` 파일이 운영체제 디렉터리에 생성됨.
  - **결론**: 사이드카 파일의 생성/참조는 SQLite WAL 모드의 엔진 레벨 reader 프로토콜에 의한 정상적인 공유 메모리 관리 동작이며, 원본 DB 본체 파일 내용과 스키마는 100% 무변경(Read-Only) 상태를 유지함.

## 5. 확인하지 않은 부분 (의도적 범위 밖)

1. **실제 프로덕션 DB 및 개인정보 미접근**: `.private/`, 실제 사용자 DB(`raider.sqlite`), 실제 SNS 로그인 세션은 사용자 정책에 따라 접근하지 않았으며, 전용 임시 SQLite fixture로만 검증함.
2. **외부 서드파티 MCP 호스트 연동**: Claude Desktop 등 외부 GUI 클라이언트에 서버를 등록하는 작업은 범위 밖으로 다루지 않았으며, 공식 Python MCP SDK(`mcp.client.stdio.stdio_client`) subprocess로 독립 검증함.
3. **네트워크 및 원격 접근**: 로컬 stdio 전용 서버이므로 외부 네트워크/HTTP/SSE 포트는 검증 대상이 아님.

## 6. 결론

T-002 조회 전용 MCP 서버(`raider_mcp.py`)는 spec에서 요구한 모든 읽기 전용 제약(`mode=ro`, `query_only`, 쓰기 차단), 3단계 안정 정렬, 엄격한 입력 검증, SQL 인젝션 방어, 300k+ 유니코드 보존, 안전한 에러 위생, stdio MCP 프로토콜 및 WAL 최신 커밋 조회를 완벽하게 충족합니다. 이에 따라 **PASS**로 판정합니다.
