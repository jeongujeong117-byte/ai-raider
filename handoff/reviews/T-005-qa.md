## 4. 3차 재검증 (S1 수정 `be09b34` 병합 후 최종 PASS)

### 4.1 S1 수정 내용 확인 (`be09b34`)
- **소비 경계 필드 검증 (`_validate_items`)**:
  - `tasks`: `id`는 필수 비어있지 않은 문자열(`str`), `status` 및 `title`은 `str | None`.
  - `workers`: `dispatchId`는 필수 비어있지 않은 문자열(`str`), `taskId/state/liveness/terminalState/outcome`은 `str | None`.
  - `nextCursor`: `str | None`.
  - 위반 시 `ValueError` 발생 → `_orca_json`에서 `(ValueError, KeyError, TypeError, RecursionError)` 캐치하여 `orca <sub> JSON 파싱 실패` (status error, exit 2)로 안전하게 격리.
- **예외 안전망**: `main()`에서 `check_orca` 호출을 try-except로 감싸 예기치 못한 내부 오류도 `orca_internal` error (exit 2)로 처리하여 raw traceback 유출을 원천 방지함.

## 5. 미확인 사항 (S4 감사 몫)

1. **플랫폼별 진입점 해석**: Windows 환경에서 `.cmd`→`.exe` sibling 해석은 실물 검증되었으나, Linux `orca-ide`/`orca-dev` 기본값은 모의 테스트로만 확인됨.
2. **실시간 관찰 불가 항목**: 워커 멈춤/응답 없음, 테스트 수 감소는 허용 자료에 직접 증거가 없어 unknown으로 안전하게 보고되며 S4 사람형 감사가 필요함.
3. **출력 한도(4MiB) 버퍼링**: `subprocess.run`의 완료 후 버퍼 길이 검사 방식(스트리밍 실시간 킬 아님)은 정상 작동하나 악의적 무한 출력에 대한 잠재적 메모리 버퍼 위험이 존재함.
