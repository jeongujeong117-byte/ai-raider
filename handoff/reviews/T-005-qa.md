## 2. 결함 재현 및 계약 위반 분석

### 2.1 결함 내용
- **재현 입력**:
  1. Orca `task-list` 응답에 `{"ok": True, "result": {"tasks": [{"id": [], "title": "T-005"}]}}` 주입
  2. 또는 Orca `worker-list` 응답에 `{"ok": True, "result": {"workers": [{"dispatchId": "ctx_01", "taskId": []}]}}` 주입
- **원인 분석**:
  - `tools/progress_check.py`의 `_orca_json`은 items의 각 원소가 `dict`인지 여부(`all(isinstance(i, dict) for i in items)`)만 검사하고 개별 필드(`id`, `taskId`)의 해시 가능성 및 타입 검증을 누락함.
  - 이후 `check_orca` 493행:
    ```python
    title_by_id = {t.get("id"): str(t.get("title", "")) for t in tasks}
    ```
    에서 `t.get("id")`가 list일 경우 dict 키로 사용할 수 없어 `TypeError: cannot use 'list' as a dict key (unhashable type: 'list')` 예외가 발생함.
  - 516행 `tid = tid_by_task.get(w.get("taskId"))`에서도 동일하게 unhashable list 키 조회 시 unhandled `TypeError` 폭발.
  - `check_orca` 함수 전체에 해당 예외 처리가 없어 `main()`을 뚫고 프로세스가 traceback과 함께 비정상 종료됨.

### 2.2 기대 동작 vs 실제 동작
| 구분 | 계약 요구사항 (기대) | 실제 동작 (결함) |
|---|---|---|
| 종료 코드 | `exit 2` (필수 소스 unavailable / 파싱 실패) | `exit 1` (Python 비정상 예외 종료) |
| stderr | 원시 traceback/비밀 유출 없이 안전한 고정 오류 출력 | 원시 Python `TypeError` Traceback 노출 |
| stdout | 스키마 준수 JSON 또는 안전 오류 요약 | 빈 문자열 (JSON 미출력) |
| check 상태 | `orca_task_list` / `orca_worker_list`: `status: "error"` | 체크 결과 생성 전 크래시 |
